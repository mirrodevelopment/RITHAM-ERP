1. What the Project Is

RITHAM ERP is a full-stack, web-based Enterprise Resource Planning system built exclusively for Ritham Garments, a multi-branch custom tailoring and garment manufacturing business.

The system manages the entire customer-to-delivery lifecycle for custom garments:
- Registering customers and capturing their body measurements
- Creating garment orders with pricing, delivery dates, and advance payments
- Routing each order through a 12-stage tailoring production pipeline
- Tracking which employee is working on each stage at any moment
- Recording all payment transactions in a full payment ledger
- Delivering completed orders and collecting final balances
- Providing business analytics, revenue reports, and stage-wise dashboards

The system runs as a single Java JAR that serves both the REST API and the HTML frontend on port 8080.

---

2. Why It Exists

Ritham Garments previously managed orders on paper or in spreadsheets. This caused:
- Orders getting lost or duplicated when multiple staff handled the same job
- No visibility into which stage a garment was at across two physical branches
- Revenue numbers miscounted because advance payments and balances were mixed
- No record of body measurements per customer for repeat orders
- Branch staff accidentally viewing or modifying orders from other locations

RITHAM ERP replaces all of this with a digital, role-enforced, multi-branch system.

7. Authentication and Authorization Architecture

Token Flow


1. POST /api/auth/login  {username, password}
       |
   AuthService.login() -> LoginRateLimiter.checkRateLimit()
       |
   AuthenticationManager.authenticate() -> BCrypt verify
       |
   JwtService.generateAccessToken()   -> 15-minute HS256 JWT
   JwtService.generateRefreshToken()  -> 7-day HS256 JWT
       |
   RefreshToken persisted in refresh_tokens table
       |
   LoginResponse {accessToken, refreshToken, employeeId, role, branchId, ...}

2. Every protected API call:
   Authorization: Bearer <accessToken>
       |
   JwtAuthFilter.doFilterInternal()
     -> extractUsername() from JWT
     -> isAccessToken() check (tokenType == "access")
     -> CustomUserDetailsService.loadUserByUsername()
     -> isTokenValid() (signature + expiry)
     -> SecurityContextHolder.setAuthentication()
     -> BranchContext.setBranchId() based on role/header
       |
   Service layer reads BranchContext.getBranchId() for data scoping

3. POST /api/auth/refresh  {refreshToken}
       |
   RefreshTokenRepository.findByToken() -> validate not expired/revoked
       |
   Rotate: mark old token isRevoked=true, issue new pair
       |
   New LoginResponse

4. POST /api/auth/logout
       |
   RefreshTokenRepository.revokeAllByEmployeeId(employeeId)


JWT Claims (Access Token)

| Claim | Value |

| sub | username (or mobile number) |
| tokenType | "access" |
| role | e.g. "ROLE_ADMIN" |
| employeeId | Long (employee primary key) |
| fullName | String |
| branchId | Long (null for global admin) |
| branchCode | String (null for global admin) |
| iat | Issued at (epoch seconds) |
| exp | Expiry (epoch seconds) |

Token Expiry
- Access token: 15 minutes (configurable via app.jwt.access-token-expiry-ms)
- Refresh token: 7 days (configurable via app.jwt.refresh-token-expiry-ms)

Password Hashing
BCrypt with cost factor 12. The DataInitializer runs on startup and calls encodeIfNeeded()
which only re-encodes a password if the stored hash is NOT already a valid BCrypt hash.
This prevents admin-changed passwords from being overwritten on restart (TASK-002 fix).

8. Multi-Tenancy (Branch Isolation)

The system supports multiple physical branches sharing one database, with row-level data
isolation enforced at the service layer.

Mechanism

BranchContext is a static ThreadLocal<Long> that holds the active branch ID for the
current HTTP request thread. Set in JwtAuthFilter, cleared in the finally block.

Rules

| User Type | branch_id in DB | BranchContext set to | Can see |

| Global Admin (admin) | NULL | null (unless X-Branch-Id header sent) | All branches |
| Global Admin with header X-Branch-Id: 2 | NULL | 2 | Branch 2 only |
| Global Admin with header X-Branch-Id: ALL | NULL | null | All branches |
| Branch Manager/Reception (e.g. manager_cbe) | 2 | 2 | Branch 2 only |

Security Alert
If a non-admin user sends the X-Branch-Id header attempting to switch branches, the filter:
1. Ignores the header (always uses their own branchId from JWT)
2. Logs an AUDIT SECURITY ALERT with the username, attempted branch ID, and request URI

Service Layer Enforcement

All repository queries accept an optional branchId parameter:
- When branchId IS NULL: returns all branches (admin global view)
- When branchId IS NOT NULL: filters to that branch only

The verifyBranchAccess(CustomerOrder order) method in OrderService is called on every
single-order read or update to prevent cross-branch data access (TASK-003 fix).

10. Login Rate Limiting

LoginRateLimiter is an in-memory ConcurrentHashMap-based rate limiter with no
external dependency (no Redis required).

| Parameter | Default | Config Key |

| Max failed attempts per username | 5 | app.rate-limit.max-attempts-per-username |
| Max failed attempts per IP | 10 | app.rate-limit.max-attempts-per-ip |
| Lockout duration | 15 minutes | app.rate-limit.lockout-duration-minutes |
| HTTP response on lockout | 429 Too Many Requests | -- |

How it works:
1. checkRateLimit(ip, username) called BEFORE any DB or BCrypt work
2. If locked -> throws AppException(RATE_LIMIT_EXCEEDED) immediately (no BCrypt cost)
3. On BadCredentialsException -> recordFailedAttempt(ip, username) increments counters
4. On success -> recordSuccessfulLogin(ip, username) clears counters
5. Entries pruned when map size exceeds 1,000
6. State lost on JVM restart (in-memory only; acceptable for internal LAN use)

13. Module: Employee

Location: src/main/java/com/ritham/erp/module/employee/

Entity: Employee -> employees table

Key fields: employeeCode (EMP-XXX format), fullName, mobileNumber, email, username,
passwordHash, role (FK -> roles), department (FK -> departments), stage (which production
stage they work at), isActive, branch (FK -> branches).

Role-Based Access:
- GET /api/employees -- any authenticated user (branch-scoped)
- POST/PUT/PATCH/DELETE -- ADMIN only (@PreAuthorize enforced at controller)

Branch scoping: EmployeeService.getEmployees() filters by BranchContext.getBranchId().
Branch staff see only their own branch's employees. Global admin sees all.

Employee code generation: Safe Java regex (^EMP-(\d+)$) to find the max numeric suffix,
then increments it. Avoids the legacy SQL CAST(SUBSTRING...) crash that caused the entire
employee screen to fail on codes like EMP-ADMIN (TASK-019 fix).

17. Order Lifecycle and State Machine

Valid Status Groups

| Group | Statuses |

| ACTIVE_PRODUCTION_STAGES | DESIGNING, LINING, HAND_MACHINE_WORK, INITIAL_IRONING, CUTTING, STRETCHING, STITCHING, HEMMING, FINAL_IRONING, QUALITY_CHECK |
| DELIVERED_STATUSES | DELIVERED, DELIVERY, COMPLETED |
| TERMINAL_STATUSES | DELIVERED, DELIVERY, COMPLETED, CANCELLED |

Transition Rules (validateStatusTransition)


PENDING -> any active production stage     ALLOWED
PENDING -> READY_TO_DELIVERY               ALLOWED
PENDING -> CANCELLED                       ALLOWED
PENDING -> DELIVERED                       BLOCKED (must pass through READY_TO_DELIVERY)

Active Stage -> any other active stage     ALLOWED (rework/reorder supported)
Active Stage -> READY_TO_DELIVERY          ALLOWED
Active Stage -> CANCELLED                  ALLOWED
Active Stage -> PENDING                    BLOCKED (cannot revert)
Active Stage -> DELIVERED                  BLOCKED (must pass READY_TO_DELIVERY first)

READY_TO_DELIVERY -> DELIVERED/DELIVERY    ALLOWED
READY_TO_DELIVERY -> any active stage      ALLOWED (rework)
READY_TO_DELIVERY -> CANCELLED             ALLOWED
READY_TO_DELIVERY -> PENDING               BLOCKED

DELIVERED / COMPLETED / CANCELLED -> any   BLOCKED (permanent terminal states)


The state machine also supports custom dynamic stages stored in the production_stages table.
These are validated via productionStageRepository.existsByStageKeyIgnoreCaseAndIsActiveTrue().

Payment Status Reconciliation

After every status update or payment, syncOrderPaymentState() recalculates:
- All payment rows summed -> paidAmount
- Payment methods collected -> paymentMode (or "SPLIT" if composite string exceeds 30 chars)
- paymentStatus = PAID if paidAmount >= netTotal
                  PARTIAL if paidAmount > 0
                  PENDING otherwise

18. Payment Ledger

Every payment creates a permanent, immutable OrderPayment row. Rows are never deleted
or updated -- the ledger is append-only.

Payment Flow at Order Creation

createOrder(req):
  advance = req.advanceAmount
  -> CustomerOrder.advanceAmount = advance
  -> CustomerOrder.paidAmount = advance
  -> OrderPayment { type=ADVANCE, method=req.paymentMode, amount=advance }


Payment Flow at Status Update

updateStatus(id, newStatus, finalPayment, paymentMode):
  if finalPayment > 0:
    remaining = netTotal - currentPaid
    if finalPayment > remaining -> VALIDATION_FAILED (overpayment rejected)
    -> paidAmount += finalPayment
    -> OrderPayment { type=FINAL or PARTIAL, method=paymentMode, amount=finalPayment }
    -> syncOrderPaymentState(order)


Standalone Payment Recording

POST /api/orders/{id}/payments
  RecordPaymentRequest { amount, paymentMethod, paymentType, collector }
  -> same validation (no overpayment)
  -> OrderPayment persisted
  -> syncOrderPaymentState(order)


Revenue Reporting Key Rule
Revenue is aggregated from order_payments.payment_date, NOT customer_orders.created_at.
This means:
- An advance of 1000 paid Monday is counted in Monday's revenue
- A balance of 3000 paid Friday is counted in Friday's revenue
(TASK-008 fix)

24. Frontend API Client (api.js)

The Api IIFE module wraps browser fetch() with:

1. Auto-attach JWT: reads Storage.getToken() -> Authorization: Bearer header
2. Auto-attach branch header: X-Branch-Id (only if not "ALL")
3. Response unwrapping: unwraps ApiResponse envelope, returns json.data
4. 401 silent refresh: on first 401, retries /api/auth/refresh; if successful,
   retries original request once with new token
5. Queue management: concurrent 401s queue behind a single refresh call
6. Redirect on auth failure: if refresh fails, clears session and goes to login
7. postPublic(): unauthenticated POST for the login endpoint only

25. Frontend Auth and Session (auth.js)

The Auth IIFE module handles:

- Auth.login(username, password): calls Api.postPublic(API.LOGIN) -> saves session
- Auth.logout(): calls Api.post(API.LOGOUT) -> clears session -> redirects to login
- Auth.guard(allowedRoles): call at top of every protected page; redirects if not
  authenticated or wrong role. Returns false if unauthorized.
- Auth.redirectToDashboard(): navigates to the role default desk
- Auth.isTokenExpired(): client-side JWT expiry check (decode without verify)

Route guard pattern used in every protected page:
  if (!Auth.guard()) return;
  if (!Auth.guard([ROLES.ADMIN, ROLES.OPERATIONS_MANAGER])) return;

27. Data Flow: Order Creation End-to-End

`
Reception staff -> Order Desk -> "New Order" button
  |
Frontend: Mobile number entered
  -> Api.get(API.CUSTOMER(mobile)) to verify customer exists
  -> Api.get to show any existing dues
  -> Prefill measurements from /api/orders/customer/{mobile}/latest-measurements
  |
Staff fills: garmentType, measurements, deliveryDate, totalAmount, advanceAmount, paymentMode
  |
Frontend: Api.post(API.ORDERS, {
  customerMobile, deliveryDate, garmentType, lining, measurements,
  totalAmount, discountAmount, advanceAmount, paymentMode
})
  |
Backend: OrderController.createOrder(@RequestBody CreateOrderRequest)
  |
OrderService.createOrder(req):
  1. customerRepository.findByCustomerMobile() -> verify customer exists
  2. Validate: total >= 0, discount <= total, advance <= netTotal
  3. Calculate paymentStatus (PENDING / PARTIAL / PAID)
  4. Resolve branch: req.branchId -> BranchContext.getBranchId() -> DEFAULT_BRANCH_ID
  5. Generate order number via DB sequence order_number_seq
  6. CustomerOrder.builder()... -> orderRepository.save()
  7. If advance > 0: OrderPayment {ADVANCE, amount=advance} -> orderPaymentRepository.save()
  8. If garmentType provided:
     -> OrderMeasurement saved (immutable snapshot)
     -> CustomerMeasurementService.saveOrUpdate() (updates customer profile)
  9. customer.incrementOrderCount() -> customerRepository.save()
  10. return orderMapper.toResponse(saved, customerName, measurements)
  |
Frontend: Order created -> show order number -> navigate to order detail desk
``

33. Known Issues and Technical Debt

In-Memory Rate Limiter State Lost on Restart
The LoginRateLimiter state is lost on every JVM restart. An attacker with access to restart
the app could clear lockouts. Acceptable for internal LAN use. For internet-facing deployments,
replace ConcurrentHashMap with Redis-backed or database-backed tracking.

OptimisticLockingFailureException Not Handled
The version column on customer_orders (V11) enables JPA @Version optimistic locking, but
ObjectOptimisticLockingFailureException is not yet mapped in GlobalExceptionHandler.
Currently falls through to the generic 500 handler with a confusing error message.
Fix: add a handler returning HTTP 409 with a clear "Order was modified by another user,
please refresh" message.

paidAmount Denormalization
paidAmount on the order is a denormalized cache of the sum of payment ledger rows.
If a payment row were directly deleted from the database outside the application,
paidAmount would become stale. The application prevents this via the API layer, but
there is no compensating re-sync mechanism outside of the application path.

production_tracking Table Unused
The production_tracking table exists in the schema (V1) but is not yet wired to any
backend service or controller. Order tracking is done entirely via customer_orders.status.
This table could support a granular per-employee, per-stage audit trail in future.

order_deliveries Table Unused
Similarly, order_deliveries exists in the schema but delivery confirmation is done via
order status (DELIVERED). The table could support multi-delivery or partial-delivery
tracking in future.

Design and Material Modules Placeholder Only
/desks/design/ and /desks/material/ are HTML placeholder pages. There is no active
controller for /api/designs or /api/materials.
